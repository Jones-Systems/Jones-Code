# Synthetic performance staging

The [staging guard](../../scripts/performance-staging/guard.mjs) allocates a new private synthetic root under an explicit HOME or worktree boundary. Supply the exact producer repository, source revision, task reference and run ID, plus explicit protected boundaries. Policy supplies boundaries and byte limits; it supplies no access authority. Protected ancestors and descendants are refused before candidate inspection. Existing destinations, aliases, symlinks, hardlinks and unexpected devices are refused. Never point this helper at live state or import a copied database to establish provenance.

Retain the original `createOwnedRoot` handle for writes and cleanup. Creation receipts are observations; JSON serialization, object spreading or copying a marker cannot create an owner. `assertOwnedDatabase` creates an absent file with `access: "create"`, or verifies a previously created file for `access: "readwrite"`. Its permit checks the exact canonical path and identity before the caller opens it. The boundary is a private root and cooperative same-UID custody. It does not protect against a malicious concurrent actor with the same UID.

An audited synthetic producer opens `permit.canonicalPath` and keeps one live resource per database. Pass that resource and its actual close operation to `observeSyntheticClose`. The callback runs once; successful completion and unchanged identities produce an opaque proof. A rejected close has an unknown effect, yields no proof, prevents retry and retains the tree. `sealSyntheticFixture` requires the original matching proof and binds the producer step, main/WAL/SHM/journal layout and a bounded file manifest with hashes. A fresh write operation requires a fresh permit and resource closure, invalidating the earlier proof and seal. Discard earlier receipts and pins when reopening. A close callback's completion relies on the audited caller; it independently attests neither producer content nor SQLite semantics.

For standalone read-only verification, pass the receipt, its independently trusted producer digest, exact expected binding and policy to `validateSyntheticFixture`. `syntheticFixtureReceiptSha256` hashes `JSON.stringify(receipt) + "\n"`; computing a digest from untrusted input does not establish provenance. Verification streams bounded files and checks identities, hashes and layout. Run it inside the worker's deadline and report verification cost separately. A marker alone is insufficient. This foundation does not qualify SQLite read-only opens, immutable mode, migration, backup or restore; those require their own actual before/after layout and database checks.

The [leaf supervisor](../../scripts/performance-staging/lifecycle.mjs) runs one owned, audited offline child with an absolute executable, argument array, explicit bounded environment, hard deadline and combined output budget. It uses no shell. It counts bytes before retaining output, terminates only the captured child PID, escalates after the grace period and awaits captured close/reap. An explicit environment does not establish network or provider containment. Descendants, servers, providers and Electron supervision are outside this helper's contract.

For cross-process production, the parent's genuine handle owns the enclosing root. The leaf receives that root as CWD/input and calls the same guard to allocate a fresh nested root with its own genuine handle. The leaf closes its resource, seals the fixture and emits a bounded receipt. After captured child close/reap, the parent pins the trusted producer output, verifies the exact nested location and expected producer binding, and validates the receipt. Reconstructing a write handle from JSON is unsupported.

Preserve required receipt evidence before `disposeOwnedRoot`. Cleanup requires the original unchanged owner, observed database closure, every genuine child receipt and a safe unchanged tree. Unknown closure, cloned receipts or changed identities retain the entire root. Successful cleanup verifies exact absence; there is no generic reset or deletion command. Tests allocate small invocation-owned roots beside the test modules, outside `/tmp`. Their `finally` cleanup closes owned file resources and aborts and awaits every captured child before removing only the captured outer fixture root. Unknown child closure retains that root and reports cleanup failure while preserving the original test failure.

The [fixture producer](../../scripts/performance-staging/fixtures.mjs) exposes three callback APIs. `withOpenSyntheticFixture(options, use)` creates a genuine in-process context for an audited offline benchmark. The context supplies the original owner, paths, Engine, snapshot query and `run(effect)`. `captureSyntheticFixture(context)` accepts only that original open context. Keep callbacks bounded, await their work through `run` and cooperate with cancellation; the enclosing leaf supervisor bounds process lifetime. The wrapper captures the final state, awaits the actual `ManagedRuntime.dispose` through the guard's close observer, seals and cleans its original root before returning `{ value, capture, captureSha256, receipt, receiptSha256, cleanup }`. Returned paths and receipts are historical evidence; the files have been removed.

`withClosedSyntheticFixture(options, use)` runs the fixed leaf producer under an original enclosing owner. After captured child close/reap, it pins the complete captured receipt and verifies the exact nested root. Use the verified database and files within the callback. Finish all reads and close every consumer resource before returning a `ClosedFixtureConsumerOutcome`: `{ schema: "jones-performance-fixture-consumer/v1", fixtureReceiptSha256: context.receiptSha256, disposition: "release" | "retain", value }`. Only a matching explicit release lets the wrapper clean its original enclosing root and return `value` with historical evidence.

A missing or malformed outcome, raw health envelope, wrong digest, explicit retention or callback rejection retains the root and reports the reason on `error.evidence.cleanup`. A validated consumer's value survives by reference on `error.evidence.value`; malformed outcomes are not copied into that evidence. A rejected callback preserves its original error. A diagnostic failure with known resource closure and reaped children may release while preserving its diagnostic value. The outcome relies on audited in-process custody and supplies neither independent attestation nor a serialized cleanup capability. Unknown resource closure, child close/reap, transport, validation or cleanup also retains the affected root. The caller owns reconciliation; these APIs provide no deletion operation.

Supply `parentPath`, one absent `childName`, `binding`, `policy` and `databaseSource`. The producer binding identifies the actual producing task and source revision; `databaseSource` independently identifies the production code that creates the database. This producer accepts only the explicitly bound `baseline` revision `e5a31aceec91484b64315c63dcce80f6e7581604` and `live-baseline` revision `414bb8da204c3275cd0b76b2ec4d74dfb09a97e4` beneath `/home/malcolmjones/Projects/Jones-Code-performance-worktrees-20261002`, both in `Jones-Systems/Jones-Code`. Their source and installed package context must remain fixed for the invocation. Node 24 or later must execute their actual TypeScript imports; an installed dependency or a type check alone does not establish import compatibility. Optional `signal` applies cancellation; `lifecycle` bounds the closed wrapper's timeout, termination grace and reap wait.

The `coherent-v1` recipe defaults to three turns and 256 payload bytes. `recipe.historyTurns` accepts 3–256 and `recipe.payloadBytes` accepts 1–65536. Real production migrations and Engine commands create the journal, receipts, projections, turns, sessions and checkpoint summaries. Production repositories create provider metadata, native creation history where present, and a retained lease with generation fencing. Checkpoint diff text and all files are synthetic. Engine-owned leases are released through its API before final capture; the dedicated lease remains. A null repository identity resolver avoids Git subprocesses. Provider execution, reactors, listeners and real Git checkpoints are outside this producer.

Captures contain counts, canonical table hashes, actual migration ledgers, observed durability, integrity and foreign-key results, replay/read-model equivalence, adjacent page cursors, lease fencing and hashes of referenced files and blobs. Physical hashes describe one fixture; independently created fixtures contain different generated identities and timestamps. Large payloads remain in the database. The complete request and one stdout envelope each have a 49 KiB limit, the complete sealed receipt has a 24 KiB limit, and the tree has a 32-entry limit. The supervisor reserves 8 KiB for stderr. Oversize output is refused; receipts are never shortened.

Omit `profile` to preserve each baseline's production defaults. Select `health-offline-delete` or `benchmark-wal` to independently seed a fresh fixture from the same source and recipe. `capture.runtime.pragmas` preserves the production observation; additive `capture.profile` records the named profile's bounded phases and maintenance evidence. Profiles never copy an existing database or establish production durability.

The health profile captures every fixed table summary and ordered migration ledger, closes the actual production runtime, and obtains a fresh permit on the same original owner. A separate client-only SQLite lifetime verifies unchanged canonical content, completes a nonbusy checkpoint, verifies the returned and observed DELETE mode, repeats content, integrity and foreign-key checks, and closes. It then reads the raw header's rollback format bytes and verifies absent WAL, SHM and journal sidecars before sealing with the final close proof. It never reopens production persistence or migrations. A shutdown content change refuses the profile.

The benchmark profile keeps the actual production WAL mode. It compares journal mode and the observed synchronous, foreign-key, busy-timeout, journal-size-limit, page-size and user-version settings at five finite phases: before and after seeding, before and after the callback, and before production close. A mismatch refuses the profile. These observations do not prove continuous monitoring or production durability. A named profile's failure, busy checkpoint, cancellation or unknown closure emits no seal and retains its root with partial evidence on `error.evidence.profile` and the cleanup reason. Reconciliation remains with the original creating owner.

Run the bounded group with:

```sh
node --test --test-concurrency=1 scripts/performance-staging/guard.test.mjs scripts/performance-staging/lifecycle.test.mjs scripts/performance-staging/fixtures.test.mjs scripts/performance-staging/migration-restore.test.mjs
```

A successful synthetic rehearsal does not promise that arbitrary later application schemas can roll back. ## Staged test-app procedure and limits

Treat the Jones source-bound fixture as an isolated synthetic test workload. A “T3 Code (Dev)” window or a Jones worktree name does not prove state, Electron-profile, provider, filesystem or network isolation. These scripts exercise production source services with synthetic files and a null repository-identity fixture; they do not start a desktop app, server listener or provider. Use the separately qualified UI workflow only after its current source/build binding and isolation probe are verified. This source harness is not an uncontained launcher fallback.

1. Verify the declared non-main worktree, source heads, clean or explicitly owned source changes, package/lock bytes and original owner. Keep all live homes, databases, credentials and shared runtime paths outside the supplied policy. Allocate fresh synthetic children only; never import private or live databases.
2. Install only the frozen worktree dependencies with `vp install --frozen-lockfile --prefer-offline`; verify unchanged manifest and lockfile bytes. Obtain the coordinator's fresh serial admission before each local test.
3. Run the focused source case, then the registered four-module union. Preserve the source/runtime/capture/close/cleanup evidence before relying on the result. All commands in this guide are staged synthetic recipes, not commands for a live application or database.
4. For a health consumer, use a separately seeded `health-offline-delete` callback lifetime and its genuine sealed receipt. For an open workload use `benchmark-wal`. Keep consumers within the callback and return the explicit closed-consumer acknowledgment only after every resource and captured child is known closed/reaped.
5. For rollback rehearsal, use the bound private native-backup and restore cases. Preserve the original backup content and actual old-version identity; require actual old414 writes and candidate rollforward. A database copy, a maximum migration ID or a successful integrity check alone cannot prove application rollback compatibility. Unknown closure or changed identity retains evidence for its original creating owner.

The candidate service launcher starts a 120-second prepared timer for a trial child (`serviceLauncher.ts`, `PREPARED_TIMEOUT_MS`). Production SQLite setup runs the unrestricted migrations, including007's partial creation-event index, before that persistence layer is available. Index construction visits the existing journal; these small synthetic runs neither measure a production-size index build nor prove that migration plus startup fits that deadline. The harness does not extend the updater timeout or exercise a real update/readiness transition.

Both rehearsed native backup outputs were observed after completion/close with header bytes18/19 equal2,2 and no WAL, SHM or journal sidecars. They restored canonical content successfully, but remain `unqualified-backup-output` for the readonly health consumer. Closed output and absent sidecars do not imply rollback-format1,1; do not relabel or silently change the backup to make it eligible. The separately seeded health profile establishes that different layout through its own qualified lifetime.

Companion synthetic files are copied and hash-checked, while the original synthetic workspace/worktree remains alive and database path references are not rewritten. This does not prove relocation, recovery after original companion paths disappear, real Git checkpoints, real provider transcripts, secrets or a complete production filesystem backup. The rehearsal directly uses native backup primitives; it does not invoke the production launcher's private backup selector, sync/rename protocol, paired settings binding, update state machine or rollback authority. It provides no backup retention policy, power-loss guarantee, production-scale performance measurement or live recovery permission. Node24/SQLite3.53.3 source results do not qualify the crashed Node26 diagnostic harness or a compiled runtime.
